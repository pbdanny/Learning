Lesson 1 · 15–20 minutes

Choose the processor before you write the pipeline

The first Document AI design decision is not “which API call?” It is “what contract do I want Google to return?” OCR, invoice parsing, form parsing, and custom extraction all return a Document, but they promise different structure.

Target outcome. For an invoice or form, produce fields that are traceable to the source PDF, validated by your application, and evaluated on a representative corpus—not merely text that looks plausible.

1. The mental model

Document AI has two layers:

  1. Processor choice determines the model capability: text/layout OCR, generic form structure, invoice semantics, or a custom schema.
  2. Your extraction contract decides what your application accepts: required fields, null policy, type normalization, evidence spans, confidence/review thresholds, and error handling.

The API request names one processor resource:

projects/{PROJECT_ID}/locations/{LOCATION}/processors/{PROCESSOR_ID}

Calling process with a PDF returns a Document. Keep the raw response. Its text is a canonical text buffer; entities and layout objects point back to it through text anchors. See the glossary.

2. The four choices that matter

Invoice ParserInvoices resemble the supported invoice domain and its supplied fields are close to your schema.Invoice entities such as supplier, invoice ID, dates, totals, tax, and line items.Every vendor layout, language, and accounting rule will be correct.

Important language test. The published Invoice Parser language list currently does not include Thai. Enterprise Document OCR is the safer baseline for Thai or mixed-language invoices, then compare a parser only on a labeled sample. Never infer support from a successful demo on English documents.

3. The recommendation for your first experiment

Run a paired baseline on the same small, representative corpus:

  1. Enterprise Document OCR: establishes whether text, reading order, and layout are sufficient across scan quality and languages.
  2. Invoice Parser for invoice-like documents and/or Form Parser for generic forms: measures the convenience of semantic extraction.

For each document, persist: source file hash, processor/version/location, raw Document JSON, parsed application record, field-level validation result, and a human-reviewed label when available. This prevents a shiny UI result from becoming an unmeasurable production dependency.

4. A minimal Python call

Install the official client and authenticate locally with Application Default Credentials:

uv add google-cloud-documentai
gcloud auth application-default login
from pathlib import Path
from google.api_core.client_options import ClientOptions
from google.cloud import documentai


def process_pdf(project_id: str, location: str, processor_id: str, path: str):
    # `location` must match the processor's location, for example "us" or "eu".
    client = documentai.DocumentProcessorServiceClient(
        client_options=ClientOptions(
            api_endpoint=f"{location}-documentai.googleapis.com"
        )
    )
    raw_document = documentai.RawDocument(
        content=Path(path).read_bytes(),
        mime_type="application/pdf",
    )
    request = documentai.ProcessRequest(
        name=client.processor_path(project_id, location, processor_id),
        raw_document=raw_document,
    )
    return client.process_document(request=request).document

This call is deliberately not an extraction pipeline. It proves only the boundary: authenticated request in, raw Document out. Next, write an adapter that turns the response into your schema and preserves evidence.

5. What failure looks like

  • OCR succeeds but values are wrong: treat it as a schema/validation problem, not proof that the OCR processor failed.
  • Invoice fields are empty or inconsistent: check processor language/layout fit before adding prompt-like repair rules.
  • Numbers look plausible but disagree with totals: flag the document for review; use arithmetic and business-rule validation.
  • A workflow has no raw response: it is not auditable and cannot be debugged reliably.
