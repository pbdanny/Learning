Build a schema adapter as a pure boundary

A schema adapter protects the rest of your system from a vendor-specific response. It takes a saved Document AI response and returns one stable, validated application record.

1. Start with the output contract

Do not begin by looping over document.entities. First define the record your database, API, or CSV should receive:

InvoiceRecord(
  invoice_number, supplier_name, invoice_date,
  net_amount, vat_amount, total_amount, currency,
  evidence
)

Each field needs a rule: accepted Document AI entity types, expected value kind, and whether absence blocks automation. This is the application contract; it is owned by you, not by Google.

2. Keep three jobs separate

LayerResponsibilityExample
Document AI clientCalls Google and saves the raw Document response.One PDF → JSON response.
Schema adapterMaps entities into your canonical fields; retains evidence.total_amount becomes a Decimal plus source span.
Validator / policyApplies business rules and routes exceptions.net + VAT == total, otherwise review.

3. The adapter algorithm

  1. Index entities by type. Never make downstream code search a list repeatedly.
  2. Select candidates deliberately. If several could populate a singular field, record ambiguity rather than silently choosing one.
  3. Parse normalized values first. Dates and money should come from the processor’s normalized value where present; do not parse locale-sensitive display text as a hidden fallback.
  4. Preserve evidence. Keep the original entity type, extracted text, confidence, page, and text-anchor offsets.
  5. Validate cross-field rules. Totals, currencies, required fields, and duplicate identifiers are business policy.
  6. Return data plus errors. A review flag is a valid output; a fabricated value is not.

4. Working starter implementation

The repository now contains examples/document_ai_schema_adapter.py. It is dependency-free and intentionally accepts a JSON-like saved Document response rather than a live Google SDK object. The test file constructs two representative responses: one valid and one where the arithmetic mismatch must trigger review.

from document_ai_schema_adapter import FieldRule, adapt_invoice

rules = {
  "invoice_number": FieldRule(("invoice_id",), "text", required=True),
  "invoice_date": FieldRule(("invoice_date",), "date", required=True),
  "total_amount": FieldRule(("total_amount",), "money", required=True),
}
result = adapt_invoice(saved_document_json, rules)

if result.needs_review:
    send_to_review(result.record, result.errors)
else:
    persist(result.record)
Configure, do not guess. The entity names in FieldRule must come from a stored sample response from the exact processor and version you selected. Different processors return different entity sets and nested structures.

5. How to use it on a real corpus

  1. Process 10–30 representative PDFs and save every raw response.
  2. Inspect actual entity types, values, confidence, and missing cases.
  3. Write the field rules from those observations.
  4. Add one failing test per known failure mode: absent total, multiple totals, wrong currency, invalid date, totals mismatch.
  5. Only then connect the adapter to the workflow or database.
