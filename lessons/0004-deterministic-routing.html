Route documents deterministically

Deterministic routing means the same verified facts always produce the same profile decision—and insufficient or conflicting facts produce a review decision rather than a guess.

1. Route on facts, not appearance

Before field extraction, establish a small set of trustworthy facts. For invoices, use the strongest available evidence in this order:

  1. Supplier tax / registration ID after format validation.
  2. Document class: invoice, receipt, credit note, purchase order.
  3. Language when it is reliably detected or explicitly selected upstream.
  4. Processor and processor version as operational metadata.

Supplier names, logo matches, filename patterns, or layout similarity can be helpful review signals, but they are weak primary routing keys: spelling, OCR quality, and branding change.

2. Define strict profile predicates

A specific profile matches only when every configured constraint matches. For example:

vendor-a-thai-invoice matches when:
  supplier_tax_id == "0105559999999"
  AND document_class == "invoice"
  AND language includes "th" or "en"

If the tax ID matches but the document is a credit note, do not reuse the invoice profile just because it belongs to the same supplier. Use the default profile or a credit-note profile.

3. Make the decision rules explicit

1. Evaluate every non-default profile.
2. Reject a profile if any configured predicate fails or is absent.
3. Score surviving profiles from stable facts:
   tax ID = 1000, document class = 100, language = 10.
4. Select a unique highest score; use priority only as a documented business override.
5. If no specific profile matches, select exactly one default profile.
6. If top profiles tie, route to REVIEW—never choose alphabetically.
Deterministic does not mean “always automatic.” A review outcome is deterministic too. It is the correct result when the evidence cannot uniquely justify one profile.

4. Working example

examples/profile_router.py is a dependency-free implementation. Its input is intentionally small:

RoutingFacts(
    supplier_tax_id="0105-5599-9999-9",
    document_class="invoice",
    languages=("th",),
)

It normalizes only identifier formatting, applies strict matching, and returns either:

RouteDecision(status="ROUTED", profile_id="vendor-a-thai-invoice", ...)
# or
RouteDecision(status="REVIEW", profile_id=None,
              reason="ambiguous profile match; no arbitrary tie-break", ...)

Retrieval practice

A PDF has Vendor A’s tax ID but is a credit note. There is no credit-note profile. What route should it take, and why is applying Vendor A’s invoice profile unsafe?

Reply in two sentences. Then say which new profile you would add only after enough reviewed credit notes accumulate.
