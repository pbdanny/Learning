Handle variation with profiles, not a giant adapter

Many invoice layouts do not require many downstream schemas. Keep one canonical invoice record. Make the adapter a router that selects a small profile and a set of field resolvers for each document family.

The rule: one stable output schema, many controlled input profiles. Never let every vendor’s PDF shape leak into your database model.

2. What a profile is

A profile is configuration plus narrowly scoped rules for a document family. It should answer:

  • When does this profile apply? Prefer supplier tax ID, registered vendor ID, language, processor type, and document class. Do not route on fuzzy supplier text alone.
  • Where can each field be found? A prioritized list of entity types, labels, or table positions.
  • What validates the result? Allowed currency, totals logic, expected tax rules, identifier format, and whether the field is required.
  • When does it stop? Ambiguity, failed validation, or poor evidence routes to review.

See reference/invoice-adapter-profile.example.json for a default profile and a Thai vendor override. The values are illustrative; replace match identifiers and entity types from your own saved corpus.

3. Resolve fields as a ranked candidate set

Do not write:

total = first_entity_of_type("total_amount")

Instead, collect candidates, evaluate them, and keep the winner and the rejected evidence:

candidates = [
  from_entity_types(["total_amount", "invoice_total"]),
  from_labels(["Grand Total", "ยอดรวมสุทธิ"]),
]
resolved = choose_one(candidates,
  requires_currency=True,
  passes_amount_rules=True,
  confidence_threshold=profile_threshold,
)

if resolved.is_ambiguous or not resolved.is_valid:
    review("total_amount", resolved.reasons)

The point is not the confidence threshold. The point is a visible decision policy that you can change and test.

4. Add profiles only when the data earns them

SituationResponse
One-off scan-quality failureReview it; do not create a vendor profile.
Repeated label alias or table layout for one supplierAdd a narrow supplier profile with tests.
Different document class, such as credit noteAdd a document-class route and a separate contract if business semantics differ.
Field is consistently unavailable from the processorUse a different processor or custom extraction experiment; do not pile up regex patches.
Several plausible values for a singular fieldEmit an ambiguity result and review it; never choose quietly.

5. Evaluate by variation cluster

An average accuracy number can hide failures. Split your test corpus by vendor, language, scan quality, document class, page count, and layout family. Measure each required field in every cluster. A profile is ready only when its target cluster has an acceptable error rate and its fallback/review behavior is tested.

6. Change process

  1. Save the raw response and a human-verified expected record for each failure.
  2. Classify the failure: routing, candidate extraction, normalization, validation, or processor capability.
  3. Add the smallest profile rule that fixes the recurring class.
  4. Add regression tests for the failing document and at least one nearby nonmatching document.
  5. Re-run the complete stratified evaluation before enabling the change.
